# 第八阶段：数据库与会议文件备份/恢复边界

**实现日期：2026 年 9 月 18 日**

## 目标与恢复对象

备份不是“把一个目录压缩起来”，而是要能回答：在某一个恢复点，数据库中的会议元数据、任务状态、转录/分析结果，以及 `data/meetings` 下的原始音频和处理文件能否一起恢复，并且恢复后仍然相互对应。

当前工具覆盖：

- MySQL 业务数据库逻辑导出（`mysqldump --single-transaction`，包含表、触发器、事件和存储过程）；
- `MEETINGMIND_DATA_DIR/meetings` 下的全部普通文件；
- 每个文件的相对路径、大小和 SHA-256；
- 会议目录 ID 与数据库 `meetings.id` 的交叉核对；
- 恢复到全新的隔离文件目录；
- 可选恢复到临时隔离 MySQL 数据库，并核对隔离数据库的会议 ID。

日志、`data/release-check` 报告、密钥、模型缓存和其他运行时临时文件不进入归档。数据库 dump 本身必然包含业务数据（可能包含转录和分析结果），因此归档必须按敏感数据处理。

## 一致性边界

跨 MySQL 和 Windows 文件系统不存在单个原子提交点，所以工具采取显式、可验证的维护窗口协议：

1. 备份前读取数据库会议 ID，并检查 `processing_jobs` 没有 `QUEUED`、`PROCESSING` 或其他未完成状态；
2. 复制会议文件时，对每个文件执行“复制前哈希 → 复制 → 复制后哈希”，文件变化则整个备份失败；
3. 使用 `mysqldump --single-transaction` 导出数据库；
4. 导出后再次读取数据库会议 ID；如果数据库发生变化则拒绝产出归档；
5. 只有数据库会议 ID 与 `data/meetings` 顶层目录完全一致时才允许创建备份；
6. 归档写入临时 `.tmp.zip`，先完整验证，再原子改名为目标文件；已有目标默认拒绝覆盖。

这仍然要求运维在维护窗口停止 API 和 Worker 的写入。工具不会假装提供跨系统事务，也不会在发现不一致时静默排除文件。

## 使用方式

在项目根目录执行。若要一次性创建、验证并进行隔离恢复演练，可使用受控 PowerShell 包装脚本；它默认只删除自己创建的 `data/restore-drill/<时间戳>` 临时目录，归档本身默认保留：

```powershell
.\scripts\validate_backup_restore.ps1
```

如果当前数据库和会议目录不一致，该脚本会在创建阶段失败，不会静默跳过文件，也不会删除源数据。

手动分步执行：

```powershell
# 创建备份；实际归档不要提交 Git，也不要放到公开目录
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
backend\.venv\Scripts\python.exe scripts\backup_restore.py backup `
  --output "data\backups\meetingmind-$stamp.zip"

# 只验证归档结构、manifest、数据库 dump 与会议文件 SHA-256
backend\.venv\Scripts\python.exe scripts\backup_restore.py verify `
  "data\backups\meetingmind-$stamp.zip"

# 恢复到不存在的新目录；同时在 Docker MySQL 中做临时隔离数据库演练。
# 默认验证后删除该隔离数据库，避免留下额外业务库；需要保留时显式加 --keep-isolated-database。
backend\.venv\Scripts\python.exe scripts\backup_restore.py restore `
  "data\backups\meetingmind-$stamp.zip" `
  --target-dir "data\restore-drill\$stamp" `
  --container meetingmind-mysql `
  --isolated-database "meetingmind_restore_$stamp"
```

`--isolated-database` 只接受字母开头、字母/数字/下划线组成的数据库名；恢复目标必须不存在。工具拒绝 ZIP 路径穿越、符号链接、篡改文件、缺失文件、数据库 dump 缺失和目标目录冲突。错误输出不包含 SQL、转录内容、模型响应或密钥。

## 加密、保留和删除策略

当前实现负责一致性和恢复验证，**不负责归档加密**。在真实部署中，归档必须放在访问控制严格的存储中，并在存储层或归档层使用经批准的加密方案；密钥不能与归档放在同一目录。建议最小策略：

- 每日全量，保留 7 个日备份；
- 每周抽样做一次隔离恢复演练；
- 备份目录权限只允许服务账号和授权运维读取；
- 删除会议后的备份生命周期单独审查：如果合规要求“永久删除”，必须从仍在保留期内的备份中一并处理或缩短保留期；
- 归档到期销毁时记录时间、范围和执行人，但日志中不写入会议内容或密钥。

这些保留、加密和删除要求仍需目标部署环境的人工批准，不能因为本地 `verify` 通过就视为完成。
